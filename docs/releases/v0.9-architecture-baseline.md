## C. Modelo v0.9 (Bounded Autonomous Operations)

El modelo de v0.9 introduce operaciones autónomas acotadas manteniendo la separación estricta:

```text
AutonomousOperation
        │
        ▼
   PlannerPort (Domain Port)
        │
        ▼
     Decision (Structured Action)
        │
        ▼
  PolicyGateway (Fail-Closed Check)
        │
        ▼
    SubmitTask (Single Discrete Step)
        │
        ▼
   CoreRuntime (Sole Execution Runtime)
        │
        ▼
    Execution (Lifecycle & Events)
        │
        ▼
   Observation (Feedback to Planner)
        │
        ▼
┌───────────────────────┐
│ Objetivo alcanzado?   │
│ Presupuesto agotado?  │
└───────────┬───────────┘
     Yes    │    No
            │
        Terminal  ───► Siguiente paso (consumiendo budget)
```

### Componentes y Contratos Clave:
1. **`AutonomousOperation`**: Entidad de dominio supervisora. Define el objetivo, el agente asignado, el presupuesto inmutable y el historial de pasos.
2. **`AutonomyBudget`**: Value Object inmutable que impone límites estrictos (`maxSteps`, `maxDurationMs`, `maxToolCalls`).
3. **`PlannerPort`**: Interfaz de dominio desacoplada para la descomposición del objetivo y la propuesta de la siguiente acción. No ejecuta código ni herramientas.
4. **`Decision`**: Estructura de acción discreta (`type: 'CONTINUE' | 'COMPLETE' | 'STOP' | 'FAIL'`).
5. **`Observation`**: Resultado estructurado de la ejecución de una tarea previa, proporcionado al planner para evaluar el avance.
6. **`PolicyGateway`**: Barrera de gobernanza continua evaluada antes de cada paso.
7. **`SubmitTask` / `CoreRuntime`**: Infraestructura existente que procesa el paso sin duplicación de lógica de ejecución.

## D. Lifecycle de `AutonomousOperation`

```text
              [ SUBMITTED ]
                    │
                    ▼
               [ RUNNING ]
                    │
   ┌────────────────┼────────────────┬────────────────┐
   │                │                │                │
   ▼                ▼                ▼                ▼
[ COMPLETED ]   [ FAILED ]     [ CANCELLED ]   [ BUDGET_EXHAUSTED ]
```

### Reglas de Transición:
- `SUBMITTED → RUNNING`: Al inicializar la primera evaluación de presupuesto y planner.
- `RUNNING → COMPLETED`: Cuando el planner o la función de evaluación determinista determina que el objetivo fue alcanzado (`Decision.type === 'COMPLETE'`).
- `RUNNING → FAILED`: Cuando ocurre un error irrecuperable en el planner, la ejecución de la tarea falla de forma terminal, o `PolicyGateway` deniega la acción propuesta.
- `RUNNING → CANCELLED`: Al recibir una señal de cancelación explícita del operador o al expirar el tiempo de reloj (`maxDurationMs`).
- `RUNNING → BUDGET_EXHAUSTED`: Cuando se alcanza `maxSteps` o `maxToolCalls` sin que el objetivo haya sido completado.
- **Invariante de Estado Terminal:** Toda transición desde `COMPLETED`, `FAILED`, `CANCELLED` o `BUDGET_EXHAUSTED` es inválida y rechazada.

## E. Autonomy Budget (Gestión y Consumo)

El presupuesto es inmutable en su definición y medible paso a paso:

```typescript
export interface AutonomyBudget {
  readonly maxSteps: number;       // e.g. 1 .. 25
  readonly maxDurationMs: number;  // e.g. 10_000 .. 300_000 ms
  readonly maxToolCalls: number;   // e.g. 1 .. 50 calls
}

export interface BudgetConsumption {
  readonly stepsUsed: number;
  readonly elapsedMs: number;
  readonly toolCallsUsed: number;
}
```

### Algoritmo de Consumo:
1. **Pre-Step Check:** Antes de invocar a `PlannerPort`, se verifica si `stepsUsed >= maxSteps`, `elapsedMs >= maxDurationMs`, o `toolCallsUsed >= maxToolCalls`.
2. Si cualquiera de los umbrales es excedido: La operación se detiene inmediatamente sin emitir nueva tarea y pasa a `BUDGET_EXHAUSTED` (o `CANCELLED` si expiró la duración).
3. **Post-Step Accumulation:** Al completar un paso en `CoreRuntime`, se incrementa `stepsUsed += 1`, se actualiza `elapsedMs = Date.now() - startedAt`, y se acumulan las herramientas invocadas en `toolCallsUsed`.

## F. Governance (Continuous Fail-Closed Enforcement)

La gobernanza opera como un filtro estricto entre `Decision` y `SubmitTask`:

```text
Decision (Proposed Action)
   ↓
PolicyGateway.evaluate({ action: 'execute_step', resource: agentId, context: { decision } })
   ├── ALLOW ────► Procede a SubmitTask -> CoreRuntime
   └── DENY ─────► Aborta inmediatamente:
                     - Status: FAILED
                     - Code: POLICY_DENIAL
                     - Evento: policy.denied
                     - Razón registrada en AuditLog
```

Si la evaluación de la política arroja una excepción no controlada, el sistema aplica la regla **Fail-Closed** (denegar por defecto y abortar).

## G. Cancellation Determinista

La cancelación puede desencadenarse por dos vías:
1. **Operador Externo:** Invocación explícita de `cancel(operationId)`.
2. **Timeout:** Verificación de `maxDurationMs` al inicio de cada iteración.

### Reglas de Cancelación:
- Si una tarea ya está ejecutándose en `CoreRuntime`, se emite la señal de cancelación al contexto de ejecución.
- La operación pasa a `CANCELLED` y emite el evento `operation.cancelled`.
- No se inician nuevos ciclos de planificación.
- La cancelación es inmediata y terminal (sin reintentos ni workers en espera).

## H. Boundaries (Límites Explícitos de v0.9)

Quedan **estrictamente prohibidos y fuera del alcance de v0.9**:
1. **Sin bucles infinitos (`while(true)` / `for(;;)`):** Toda ejecución debe tener una condición de salida acotada por `AutonomyBudget`.
2. **Sin Agentes Autónomos Rezagados:** `Agent` sigue siendo un perfil declarativo. No contiene bucles.
3. **Sin Daemons ni Workers en Background:** No se incorporan cron jobs, workers huérfanos o hilos secundarios desatendidos.
4. **Sin Auto-Modificación:** Las operaciones no pueden modificar el código, los prompts de sistema, las herramientas autorizadas ni sus propias políticas.
5. **Sin Swarms ni Recursión:** No se permite que un agente instancie o delegue tareas en otros agentes (`No Agent-to-Agent spawning`).
6. **Sin SDKs de Proveedores en el Core:** El core permanece 100% agnóstico a OpenAI, Anthropic, Google o herramientas de terceros.
7. **Zero Runtime Dependencies:** Ninguna biblioteca externa de npm en producción.

## I. Testing Strategy para la Implementación de v0.9

La implementación futura deberá seguir la disciplina **Test-First**, cubriendo:
1. **`AutonomyBudget` Unit Tests:** Validación de límites numéricos, inmutabilidad, cálculo de consumo, y detección de agotamiento.
2. **`AutonomousOperation` Unit Tests:** Máquina de estados, transiciones válidas e inválidas, estados terminales.
3. **`PlannerPort` Contract Tests:** Verificación de contratos con stubs deterministas, manejo de decisiones válidas y malformadas.
4. **Governance Integration Tests:** Verificación de que toda propuesta de acción pasa por `PolicyGateway` y falla cerrado ante denegación o error.
5. **Runtime Integration Tests:** Verificación de que cada paso se ejecuta a través de `SubmitTask` -> `CoreRuntime` -> `Execution`, sin existencia de runtimes alternativos.
6. **Cancellation & Boundary Tests:** Verificación de detención determinista por timeout, cancelación manual, y respeto de cuotas de herramientas sin loops infinitos.
